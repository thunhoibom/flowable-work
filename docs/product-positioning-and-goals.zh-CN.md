# Workflow Agent 产品定位与目标

更新时间：2026-08-17
状态：产品方向基线

## 1. 一句话定位

Workflow Agent 是一个基于 Flowable OSS 的开源、Java-first 企业人机协作工作流平台。平台在 Flowable 执行原语之上提供可直接使用的审批业务语义，并让人、规则、业务系统和 Agent 在长期、可追溯的 BPMN 流程中可靠协作。

本项目不替代 Flowable，不复制 Dify，也不以堆叠最多的 AI 功能为目标。项目关注的是二者之间仍然存在的工程空白：把成熟流程引擎、企业审批语义和受治理的 Agent Runtime 组合成可落地的平台能力。

## 2. 要解决的问题

Flowable OSS 提供流程定义、执行、任务、历史和多实例等可靠原语，但企业应用仍需自行建设审批动作、参与人策略、租户隔离、权限、表单、审计、通知、SLA 和异常恢复。直接调用引擎 API 并不等于拥有一套可供业务使用的工作流平台。

通用 Agent 平台擅长模型、提示词、知识和工具编排，但通常不以长期企业流程、人工任务权责、事务边界、补偿、合规审计和流程版本为核心。

Workflow Agent 解决以下组合问题：

1. 将 Flowable 技术能力封装为稳定的企业工作流业务语义。
2. 让 Agent 成为受流程约束、可追踪、可恢复的参与者，而不是流程事实的控制者。
3. 统一管理流程、Agent、规则、知识、工具、权限和版本之间的发布关系。
4. 覆盖设计、测试、发布、运行、审计和优化的完整生命周期。

## 3. 目标用户

首要目标用户：

- 使用 Flowable OSS、自研审批或工单平台的 Java/Spring 团队。
- 需要私有部署、多租户、可审计和人工审批边界的企业团队。
- 希望引入 Agent，但不能接受模型直接控制业务状态或任意调用企业工具的团队。
- 希望以开放、透明、可二次开发的方式建设人机协作流程的开发者。

非首要目标用户：

- 已采购并完整采用 Flowable Enterprise 全套能力，且不需要开放实现或定制边界的组织。
- 只需要快速搭建聊天机器人、Prompt 应用或短时 AI DAG 的用户。
- 需要无代码通用集成市场，但不关心 BPMN、长期任务和企业审批语义的用户。

## 4. 与现有产品的边界

| 对象 | 已有优势 | Workflow Agent 的关系与差异 |
| --- | --- | --- |
| Flowable OSS | 成熟 BPMN/CMMN/DMN 执行原语、任务与历史数据 | 作为流程内核使用；在其上补齐审批语义、多租户治理、平台 API 和人机协作能力 |
| Flowable Enterprise | 完整商业建模、运行、Agent 和运营产品 | 作为重要参考但不复制；本项目强调开源、轻量、Java 深度集成、实现透明和可定制 |
| Dify | AI 应用、Prompt、知识、工具和模型生态 | 借鉴 Provider、RAG、评测和发布体验；不采用 Agent DAG 作为企业流程的最终权威 |
| LangGraph 等 Agent Runtime | Agent 状态图、Checkpoint、Interrupt 和多 Agent 能力 | 借鉴运行时语义；是否引入库由适配收益决定，不让其取代 BPMN 业务编排 |

竞争策略不是与 Flowable Enterprise 比较功能总量，也不是复刻 Dify 的画布。项目必须在以下组合上形成清晰价值：

> 开源 Flowable 平台化封装 + 企业审批业务语义 + 可持久化 Agent Runtime + 人机协作治理 + 协作流程自动生成。

### 4.1 与 Flowable Enterprise 的明确差异

Flowable Enterprise 已经验证了 BPMN 中配置和运行 Agent 的产品方向，因此“我们也有 Agent 节点”不能作为核心卖点。Workflow Agent 的差异必须落在平台闭环和治理语义上：

| 能力层 | Flowable 的关注点 | Workflow Agent 的关注点 |
| --- | --- | --- |
| 流程执行 | 提供成熟的 BPMN、任务、异步执行和流程历史 | 复用 Flowable，不自行实现流程执行引擎 |
| 企业业务层 | 提供流程引擎和产品能力边界 | 将审批、参与人、租户、权限、表单、审计、SLA 和异常处理收敛为稳定业务语义 |
| Agent 运行 | 提供 Agent/模型接入能力 | 提供 AgentRun、Attempt、Step、Checkpoint、租约、重试、配额、结果策略和可恢复执行 |
| 人机协作 | 支持 Agent 参与流程 | 让 Agent 先观察、建议和受监督执行，再依据运行证据在特定任务和风险范围内获得受约束完成权 |
| 责任与证据 | 记录流程和执行事实 | 分离保存 Agent 建议、人工决定、最终决定和下游结果，支持回放、评测、升级和降级 |
| 设计时智能 | 提供自身产品内的建模与 Agent 能力 | 生成包含人工、规则、Agent、知识、工具、失败策略和测试报告的协作流程草案，并经过确定性校验后发布 |

因此项目不应宣称“替代 Flowable Enterprise”，而应明确宣称：

> 在 Flowable 执行原语之上，提供开源、可定制、面向多租户企业场景的人机协作 Agent 治理平台。

如果某项功能只是重复 Flowable 已经成熟解决的流程执行能力，就不进入核心路线；只有能够降低企业接入 Agent、治理 Agent 和维护长期流程的成本，才属于本项目的核心价值。

## 5. 核心产品支柱

### 5.1 企业工作流业务语义

平台向业务系统提供稳定领域命令，而不是暴露零散 Flowable API：

- 发起、审批、驳回、退回、撤回、转办、委派和认领。
- 会签、或签、加签、减签和动态参与人策略。
- 候选人、候选组、组织目录、表单、通知、SLA、升级和异常兜底。
- 多租户、权限、审计、幂等、版本和流程运行诊断。

这部分是平台成立的基础，也是 Agent 能够安全进入企业流程的前提。

### 5.2 受治理的人机协作

首批稳定协作模式为：

- 自主 Agent 节点：执行结构化分析或处理，成功后可靠恢复流程。
- Agent 建议、人工决策：Agent 给出证据和建议，最终业务动作由人完成。
- User Task Copilot：围绕当前任务对话、补充材料、生成表单草稿。
- 失败或低置信度转人工：空结果、证据不足、超时和策略拒绝进入明确人工路径。
- Agent 提取事实、规则作出确定性判断：模型不直接承担高风险决策权。

人机协作的长期主线是“证据驱动的渐进式自治”，而不是一次性授予 Agent 全自动权限：

```text
HUMAN_ONLY
    -> SHADOW
    -> ADVISORY
    -> SUPERVISED
    -> CONSTRAINED_AUTONOMOUS
```

每次任务激活都必须固化 `AgentVersion`、自治策略版本、任务风险、输入指纹和
`taskActivationId`。有效自治等级取 BPMN 上限、租户安全策略、任务风险、Agent 质量门禁和
当前发布策略中最严格的边界。模型自报置信度不能单独获得完成权，高风险动作必须由人工或
确定性规则授权；质量回退时只能自动降级或冻结，不能自动扩大权限。

Agent 建议、人工决定、最终生效决定和下游业务结果必须分别记录。Agent 只能提交受约束的
“建议完成命令”，最终任务状态仍由 `workflow-engine` 校验并修改，`agent-engine` 不直接调用
Flowable `TaskService`。

### 5.3 可持久化 Agent Runtime

Agent 执行必须具备 Run、Attempt、Step、Checkpoint、租约、幂等、重试、取消、预算、证据、Guardrail、人工中断和审计。模型与工具调用不能占用 Flowable 事务，也不能依赖 Web 请求存活。

平台必须支持云端模型、本地模型和远程 Agent Provider，但凭据、工具权限、数据范围和成本策略始终由租户与平台共同治理。

### 5.4 人机协作流程生成器

生成目标不是一份表面可渲染的 BPMN XML，而是一份可验证、可发布的人机协作流程草案。推荐链路为：

```text
自然语言需求
→ 需求抽取与歧义确认
→ 版本化语义 IR
→ 流程骨架生成
→ 节点、参与人、表单、规则和异常路径填充
→ Agent/知识/工具/人工策略草案
→ 确定性编译为 BPMN
→ 静态校验、场景测试和 Agent Eval
→ 人工审阅
→ 发布草案
```

LLM 不直接生成最终 BPMN XML 或图形坐标。BPMN 由确定性编译器和布局器产生；修复使用受约束的领域命令或 JSON Patch；生成结果不得跳过人工审阅直接发布。

最终制品 `CollaborativeProcessDraft` 应关联流程语义 IR、BPMN 草案、AgentVersion 草案、输入输出 Schema、知识与工具绑定、人工确认策略、失败策略、场景测试和发布报告。

### 5.5 知识与工具能力

知识库不是新的流程核心，而是 Agent Runtime 的受治理能力端口。平台可以提供轻量内置实现，并允许通过适配器接入外部 RAG、Elasticsearch、Dify Knowledge、MCP 或企业数据服务。

工具必须经过平台注册、租户授权和 AgentVersion 选择，具备 Schema、身份、风险等级、超时、幂等、审计和可选人工确认。模型只能看到允许的工具描述，不能读取凭据。

### 5.6 流程智能

在积累真实运行证据后，平台可提供流程瓶颈分析、Agent 质量评估、检索质量评估、成本分析、异常路径发现和受约束的流程优化建议。优化建议默认不自动修改生产流程。

### 5.7 平台能力的取舍原则

RAG、MCP、远程 Agent、KV/Prompt Cache、多 Agent 和知识库都可以作为能力适配器逐步接入，
但它们不是项目定位本身。新增能力必须复用既有的版本、租户、权限、预算、审计、运行账本和
结果策略，不能另起一套执行状态或绕过 BPMN 业务边界。

流程生成器属于设计时 Copilot，不属于新的流程执行引擎；它只能生成可编辑草案，不能直接发布
生产流程。每个生成结果都必须经过语义 IR、确定性 BPMN 编译、路径校验、场景测试、Agent Eval
和有权限用户审阅。

## 6. 产品原则

1. BPMN 是长期业务流程和人工任务状态的唯一权威。
2. Agent 输出默认是结构化数据或建议，高风险动作必须由规则或人工授权。
3. 所有配置、运行和发布必须租户隔离、版本化、可审计、可恢复。
4. 业务语义与运行优化分离；缓存、模型路由和 Token 优化不得改变业务结果契约。
5. 先完成纵向闭环，再扩展 Provider、连接器、知识库和多 Agent 数量。
6. 新技术通过能力端口、适配器或实验区接入，不侵入工作流、权限、审计和可靠性核心。
7. 设计文档描述目标，功能完成状态必须以代码、测试和状态文档为准。

## 7. 明确不做

- 自研 BPMN 执行引擎或替代 Flowable。
- 复制 Flowable Enterprise 的全部商业产品能力。
- 复制 Dify 的通用 AI 应用画布和插件市场。
- 让租户上传任意 Java、脚本或未经治理的可执行代码。
- 让模型绕过权限、审计和人工确认直接修改流程状态。
- 依赖 Prompt 承担访问控制、业务约束和安全策略。
- 为追逐新技术破坏既有领域模型、事件协议或发布兼容性。

## 8. 分阶段目标

### 阶段 1：生产基线与工作流语义

- 完成身份会话、租户隔离、审计、可观测性、备份恢复和全链路测试。
- 建立任务中心、组织与候选组、表单、通知、委托、SLA 和升级。
- 将审批、驳回、退回、转办、会签、加减签等操作收敛为稳定领域命令。

完成标准：典型企业审批可以通过平台能力配置和运行，业务系统无需理解 Flowable 内部 API 或技术变量。

### 阶段 2：Agent Runtime 生产闭环

- 完成结果 Schema/策略校验、租约续约与接管、取消、超时和故障恢复。
- 完成 Provider 出站防护、独立有界执行器、预算、审计和故障测试。
- 打通 BPMN Agent 节点的创建运行、异步执行、完成事件和可靠恢复。

完成标准：Worker 或 Provider 故障不会造成流程丢失、重复推进、跨租户访问或错误结果静默成功。

### 阶段 3：人机协作闭环

- 实现自主 Agent 节点、人工复核、User Task Copilot 和人工接管。
- 实现 `SHADOW`、`ADVISORY` 和 `SUPERVISED` 三个渐进式自治等级；第一阶段不授予 Agent 无边界的自动完成权。
- 实现受治理工具、只读知识检索、引用证据、Guardrail 和最小评测集。
- 提供运行诊断、失败恢复、成本和质量视图。

完成标准：至少一个真实业务样例覆盖人、Agent、规则和工具协作，并通过重启、超时、空结果、部分失败和越权测试。

### 阶段 4：人机协作流程生成

- 建立语义 IR、骨架生成、细节填充、确定性 BPMN 编译和自动布局。
- 同时生成 Agent、规则、参与人、知识、工具、失败策略和测试草案。
- 建立静态检查、路径测试、Agent Eval、修复建议和人工发布门禁。

完成标准：从一段业务需求生成可解释、可修改、测试通过的协作流程草案，而不是仅生成一份 XML。

生成器的验收重点不是 BPMN XML 是否能够渲染，而是生成结果是否同时具备：人工任务边界、
Agent 版本绑定、输入输出 Schema、规则和参与人策略、知识与工具权限、失败与人工接管路径、
场景测试以及可追溯的发布报告。

### 阶段 5：知识、连接器与生态

- 扩展文档摄取、混合检索、Rerank、质量评估和外部知识适配。
- 扩展 OpenAPI、MCP、OAuth 委托和远程 Agent 协议。
- 沉淀审批、工单、合同等可验证模板，但不向核心硬编码行业逻辑。

### 阶段 6：流程智能与持续优化

- 基于运行证据评估流程效率、Agent 质量、检索召回、人工接受率和成本。
- 提供版本对比、回归评测、优化建议和受控灰度发布。
- 保持人工审批和版本发布边界，不自动修改生产流程或 Prompt。

## 9. 半年目标与成功判据

半年业余开发周期的主目标不是覆盖所有阶段，而是形成一个可以公开演示、可靠验证和持续扩展的纵向产品闭环：

```text
配置企业审批语义
→ 发布含 Agent 的 BPMN 流程
→ 人、规则、Agent 和受治理工具共同执行
→ 故障后可靠恢复
→ 查看完整流程与 Agent 审计
→ 从自然语言生成同类协作流程草案并通过测试
```

优先完成阶段 1 至阶段 4 的关键闭环；阶段 5 只实现支撑示例所需的最小知识与连接器能力，阶段 6 先建立数据和指标基础。

可以对外宣称“生产导向”前，至少满足：

1. 一个真实业务样例覆盖审批、会签或异常处理，以及 Agent、规则、知识/工具和人工复核。
2. 重复事件、Worker 重启、Provider 超时、空结果、部分结果、越权调用和跨租户访问均有自动化测试。
3. 任一次流程运行都能关联流程版本、AgentVersion、输入摘要、证据、工具调用、Token、费用、人工操作和最终结果。
4. 新用户可以通过公开文档和容器编排完成部署、建模、运行与故障查看。
5. 协作流程生成器能够产出可编辑草案、校验报告和测试结果，而非只展示生成 XML。
6. README、架构文档、状态文档和实际代码不存在“规划能力被描述为已完成”的情况。

Star 数和功能数量不是架构完成标准。真实使用反馈、可复现演示、故障测试和贡献者可理解性才是本阶段的有效信号。

## 10. 决策门槛

新增平台级能力前必须回答：

1. 它是否增强企业工作流业务语义、人机协作治理或完整生命周期？
2. 它属于 Flowable、Workflow Agent 领域层、Agent Runtime，还是外部适配器？
3. 它如何处理租户、权限、版本、审计、幂等、失败和恢复？
4. 它是否可以通过稳定契约接入，而不破坏第一阶段设计？
5. 有无真实用例和自动化验收，还是只增加技术展示？

无法明确回答时，该能力不进入核心路线。
